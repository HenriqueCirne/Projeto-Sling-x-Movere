## Story

**As a** gestor,
**I want** fazer login com credenciais restritas,
**so that** apenas a gestão autorizada acesse os dados comerciais.

## Acceptance Criteria

1. Existe uma tela de login funcional.
2. Usuários não autenticados são redirecionados para o login ao tentar acessar qualquer rota do dashboard.
3. Credenciais inválidas exibem mensagem de erro clara.
4. Sessão autenticada persiste entre navegações (cookie/sessão segura).
5. Existe um caminho documentado e reproduzível para provisionar o(s) gestor(es) inicial(is) (ex: script de seed ou comando CLI), de forma que o login com credenciais válidas seja demonstrável e testável — sem cadastro público/self-service (NFR3).

**AC1 — Tela de login.** `/login` (`packages/web/src/app/login/page.tsx`) com `LoginForm`
(React Hook Form + Zod), redireciona quem já tem sessão válida direto ao destino.

**AC2 — Redirecionamento de rotas protegidas.** Dupla camada: `src/proxy.ts` (checagem
otimista de presença de cookie, substitui `middleware.ts` no Next 16+) + `auth()` no
Server Component `app/(protected)/layout.tsx` (autorização autoritativa, consulta a
tabela `sessions`). `callbackUrl` é sanitizado (`route-guard.service.ts`) contra open
redirect (URL absoluta, `//host`, `/\host`, caracteres de controle).

**AC3 — Mensagem de erro genérica.** `INVALID_CREDENTIALS_MESSAGE` é idêntica para
e-mail inexistente e senha errada. `CredentialsService` consome uma verificação de hash
"no vazio" quando o e-mail não existe, equalizando o tempo de resposta — sem isso, a
diferença de latência seria um oráculo de enumeração de usuários mesmo com mensagem
única na tela.

**AC4 — Sessão segura e persistente.** Sessão em BANCO (não JWT stateless) via
`@auth/prisma-adapter` (TD-01) — revogar um gestor é deletar a linha em `sessions`,
efeito imediato. Cookie `HttpOnly`/`SameSite=Lax`/`Secure` (produção). Janela deslizante
de 8h (`SESSION_MAX_AGE_SECONDS` + `SESSION_UPDATE_AGE_SECONDS`). Logout
(`logoutAction` → `signOut`) apaga a sessão no banco, não só o cookie.

**AC5 — Provisionamento do gestor inicial.** `prisma/seed.ts` (`npm run db:seed`),
idempotente — e-mail já existente não é tocado (nem a senha é sobrescrita). Senha via
`SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`/`SEED_ADMIN_NAME` (env), nunca hardcoded
(NFR4). Mínimo de 12 caracteres para a senha semeada (não se aplica ao login, para não
vazar o formato de senha válida a um atacante).

**Decisões de arquitetura relevantes para o @qa** (já registradas no código, resumidas
aqui):

- **Sessão em banco com Credentials provider** exige não declarar
  `session.strategy: 'database'` explicitamente (o Auth.js recusa a forma explícita
  com um único provider Credentials) e sobrescrever `jwt.encode` para trocar o JWT por
  um `sessionToken` persistido — documentado em `auth.config.ts`.
- **Callback `session` é lista de permissão explícita**, não spread do retorno padrão
  do adapter — o padrão vazaria `passwordHash` e o próprio `sessionToken` para
  `/api/auth/session`, legível por JS da página.
- **`@node-rs/argon2` marcado `serverExternalPackages`** em `next.config.ts` — é addon
  nativo (`.node`); empacotá-lo quebra em runtime.
- **Módulos compartilhados com `prisma/seed.ts`** (`password.service.ts`,
  `credentials.schema.ts`, `seed-admin.service.ts`) importam apenas de `node_modules`,
  nunca alias `@/...` nem `next/*` — o seed roda via `tsx` fora do bundle Next.js.
- **Migração `20260827210000_add_auth_models`** gerada com
  `prisma migrate diff --from-empty --to-schema-datamodel` (sem shadow database, que
  exigiria Docker) — equivalente aqui porque `0_init` não cria nenhum objeto. Validada
  com `npx prisma validate` (schema válido); não aplicada contra Postgres real (mesma
  limitação L1 da Story 1.1).

nesta máquina** (`docker --version` → command not found; `wsl.exe` → "Subsistema do
Windows para Linux não está instalado", reconfirmado nesta sessão). Consequências:
- A migração de auth não foi aplicada contra um Postgres real; o fluxo de login não foi
  exercitado de ponta a ponta com banco de verdade.
- CodeRabbit pulado (graceful degradation — WSL ausente).
- Teste E2E (Playwright) não implementado: sem Docker não há Postgres para seedar um

### Refactoring Performed

- **File**: `packages/web/src/features/auth/auth.config.test.ts` (novo)
  - **Change**: adicionados 6 testes cobrindo `authConfig` — atributos do cookie de sessão (`HttpOnly`/`SameSite=Lax`/`Secure` só em produção), janela de sessão, páginas de login/erro, allowlist do callback `session` (nunca vaza `passwordHash`/`sessionToken`), e que existe exatamente um provider (Credentials).
  - **Why**: `authConfig` é exatamente o **Primary Focus** que o CodeRabbit desta story pediu para vigiar (cookies HttpOnly/Secure/SameSite) e não tinha nenhum teste — só revisão manual de código. É um objeto de configuração puro; importá-lo não toca o banco (`PrismaAdapter` só acessa o client quando um método é chamado).
  - **How**: fecha o risco de uma regressão silenciosa (ex: alguém remove `httpOnly` ou troca `sameSite` para `none`) passar despercebida por não quebrar nenhum teste existente.
- **File**: `README.md`
  - **Change**: documentado `npm run db:seed` no fluxo de Setup e na tabela de Comandos, mencionada a rota `/login`, adicionada linha "Autenticação" na tabela de Stack.
  - **Why**: a AC5 exige um caminho "documentado e reproduzível" para provisionar o gestor inicial. O script existia e funcionava (testado, idempotente), mas o único documento operacional do projeto (o mesmo README que documenta `docker-compose`/`db:deploy` da Story 1.1) não mencionava o seed nem a existência da tela de login.
  - **How**: um operador seguindo o README do início ao fim agora consegue chegar a um login funcional sem precisar ler comentários de código-fonte.
