## Story

**As a** developer,
**I want** um schema de banco de dados que espelhe os campos dos lançamentos de venda do ERP (Loja, Cliente, Item, Família/Grupo/Marca/Linha, Atendente, Preço, Prazo Médio, Condição de Pagamento, Data de Emissão),
**so that** todos os 8 relatórios possam ser calculados via consultas SQL.

## Acceptance Criteria

1. Tabela `sales_entries` (ou equivalente) criada com todos os campos necessários aos 8 relatórios.
2. Migração versionada e documentada.
3. Índices criados nos campos usados para filtros/agregações (Data de Emissão, Loja, Cliente, Atendente).

## Dev Notes

**Previous Story Insights**: Depende da Story 1.1 (banco de dados e ORM configurados). Revisar o Dev Agent Record da 1.1 para confirmar a tecnologia de banco efetivamente usada antes de escrever o schema.

**Data Models**: Campos obrigatórios da tabela `sales_entries` (citados textualmente na epic e nos FRs): Loja, Cliente, Item, Família/Grupo/Marca/Linha, Atendente, Preço, Tipo de Preço (necessário para FR8 — relatório "Tipo de Preço × Loja × Item"), Prazo Médio, Condição de Pagamento, Data de Emissão, além de Quantidade e Valor/Faturamento (necessários para os KPIs do Painel — FR1) [Source: docs/prd/epic-1-fundao-autenticao-e-integrao-com-erp.md#Story 1.3; docs/prd/requirements.md#Functional]. Nenhum schema formal (tipos exatos, tamanhos, nullability) foi definido em architecture docs — o data-engineer deve inferir tipos razoáveis (ex: Data de Emissão como `date`/`timestamp`, Preço/Valor como `decimal`) e evitar `float` para campos monetários.

**API Specifications**: N/A diretamente nesta story — mas o schema deve ser compatível com o payload que a API Moveres Software retornará na Story 1.4. Como a cobertura exata de campos da API Moveres ainda é um risco em aberto [Source: docs/brief.md#Key Risks], o data-engineer deve permitir nulos em campos cuja origem na API ainda não foi validada, revisitando o schema na Story 1.4 se necessário.

**Component Specifications**: N/A (story de backend/dados, sem UI).

**File Locations**: Schema Prisma em `packages/web/prisma/schema.prisma` (ou caminho equivalente ao ORM confirmado na Story 1.1); migrações em `packages/web/prisma/migrations/`.

**Testing Requirements**: Integração (migração aplica/reverte, query por campo indexado) [Source: docs/prd/technical-assumptions.md#Testing Requirements: Unit + Integration].

**Technical Constraints**:
- NFR2: performance de poucos segundos por relatório mesmo com volume crescente de lançamentos — justifica os índices do AC3 [Source: docs/prd/requirements.md#Non Functional].
- Banco de dados ainda "não confirmado" na Story 1.1 — se ainda pendente quando esta story iniciar, o data-engineer deve seguir a mesma decisão de trabalho (PostgreSQL) documentada na Story 1.1 para manter coerência entre stories.
- Nenhum documento de arquitetura (`docs/architecture/`) existe ainda neste projeto.

**Dependencies**: Depende da Story 1.1. Pode ser desenvolvida em paralelo com a Story 1.2. A Story 1.4 (sincronização) depende desta story (precisa da tabela `sales_entries` para gravar os dados sincronizados).

### Testing

- **Test file location**: `packages/web/prisma/` ou `packages/web/test/db/` conforme convenção adotada na Story 1.1
- **Testing framework**: Vitest (testes de integração com banco de teste/local)
- **Cenários mínimos**: aplicar migração, inserir registro de exemplo, consultar por Data de Emissão/Loja/Cliente/Atendente, reverter migração.
